# スキル / プラグイン導入前チェック(1ページ)

IMPROVEMENT_PLAN_2026-10.md の H8。外から持ってきたスキル・プラグイン・MCPサーバーを入れる前に、
次の3つだけを順に確認する。**1つでも「いいえ」なら入れない**(迷ったら、まず隔離した環境で試す)。

## 1. 出典は信頼できるか

- [ ] 配布元(作者・リポジトリ・レジストリ)が分かる。名前だけ似た別物ではない
- [ ] 公開されたコードで、中身を読める(ビルド済みの塊だけではない)
- [ ] 更新が続いている、または固定したバージョン(コミット)を指定できる
- [ ] 監査・評価のページがあれば見た(skills.sh 等の監査結果。無い場合は「無い」と記録する)

## 2. SKILL.md(説明・命令)に不審な点はないか

- [ ] `SKILL.md` と、同梱のスクリプト・フックを**実際に全部読んだ**
- [ ] 説明と無関係な命令(秘密情報の読み取り、外部への送信、自分自身の書き換え、勝手なインストール)が無い
- [ ] 実行するコマンドに、取得したテキストをそのままシェルへ渡す箇所(インジェクションの入口)が無い
- [ ] ダウンロードして実行する処理があれば、その取得元と固定方法(ハッシュ・バージョン)が書かれている

## 3. 権限は最小か

- [ ] 必要なツール・ディレクトリ・ネットワーク先だけを許可する(「全許可」にしない)
- [ ] 秘密情報(APIキー・トークン)を渡す必要が本当にあるか。渡すなら、そのツール専用の最小権限のキーにする
- [ ] 隔離方式を決めた([registry.yaml](../hub/registry.yaml) の `isolation`: none / sandbox-bash / container / vm)

### 隔離方式の選び方(3軸)

| 軸 | 見ること |
|---|---|
| 何が分離されるか | ファイル・ネットワーク・プロセスのうち、守りたいもの |
| Dockerは要るか | `container` / `vm` は導入と起動の手間が増える。`sandbox-bash` は軽いが分離は弱い |
| 手間 | 毎回の起動・更新・デバッグの面倒さ。続かない方式は、結局使われない |

## 記録

導入したら、上の3つの結果を1行ずつ残す(日付・出典・確認した人・隔離方式)。後から「なぜ入れたか」を辿れるようにするため。
