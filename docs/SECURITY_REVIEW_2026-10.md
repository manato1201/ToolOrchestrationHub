# Hub自身のセキュリティ点検(2026-10)

[IMPROVEMENT_DESIGN_2026-10.md](../IMPROVEMENT_DESIGN_2026-10.md) の「外部リソースの追補(2026-10-22)」X2
(「ハブ自体の認証・Webhook・APIキーの点検。結果は 確定 / 要確認 / 却下 で記録」)に沿った点検の記録。
進め方は X2 の6段階(偵察 → 探索 → 候補の反証 → 構造化 → 独立検証 → 報告)を、人手で小さくなぞった。

**独立検証についての注意**: X2 の核は「検証役を別のエージェントにする」こと。今回の検証は、**同じ作業の中で、
修正前のコードに対して実際に再現してから直し、再現をテストに残す**方法で行った。別のエージェントによる検証はしていない。
そのため「確定」の項目は再現済みだが、「点検の漏れが無いこと」までは保証できない。

## 偵察: Hubの面

- localhost(既定 127.0.0.1:8790)のHTTP API。**認証なし**。
- 状態を変える操作: 起動(`POST /api/repos/{id}/launch/{i}`)、git pull(`/sync`)、フォルダを開く(`/open-folder`)、
  台帳の再読込、スヌーズ、アラートの受信(`/api/alerts/*`、`/api/heartbeat/*`、`/api/ci-success/*`)。
- 外へ出る通信: Slack Webhook(環境変数 `HUB_SLACK_WEBHOOK_URL`)、リポジトリへの `git fetch`。
- 秘密情報: Hubのコードには保存していない(Webhook URLは環境変数のみ)。

## 確定(再現して修正した)

| ID | 内容 | 再現 | 修正 |
|---|---|---|---|
| S1 | **別サイトからの変更操作(CSRF)**。ブラウザで別のサイトを開くだけで、そのページが `POST /api/repos/{id}/launch/0` などを本文なしの単純なPOSTで送れ、**実行された**(起動・git pull・フォルダ表示・スヌーズ) | `Origin: https://evil.example` のPOSTが 200 で `launch` が呼ばれた | 変更操作のOriginが、リクエスト自身のHost(ホスト+ポート)と一致しなければ 403。Originを付けないクライアント(curl・各ツールのheartbeat/アラート送信)は通す |
| S2 | **DNS rebinding**。Hostヘッダを検査しておらず、攻撃者のドメインが 127.0.0.1 に解決されると、同一オリジンとしてアラートやパスを読まれうる | `Host: rebind.evil.example` の GET が 200 | Hostを許可リスト(既定はループバックのみ)で検査して 403。LAN等で開く場合は `HUB_ALLOWED_HOSTS` に足す |
| S3 | スヌーズの入力検証漏れ。`NaN` / `Infinity` / 巨大な値で **500**、上限も無く実質「永久に通知しない」設定を入れられた | `minutes` に `1e12` / `inf` / `nan` で例外 | 有限の正の数・最大7日に限定して 400 |
| S4 | 外部から届くアラート本文の長さに上限が無い(認証の無いAPIで、メモリ・SQLite・画面を膨らませられる) | 5000文字がそのまま保存された | 1000文字で切る。文字列以外は文字列にする |
| S5 | CSVエクスポートのインジェクション。アラート本文は外部の値で、`=` `+` `-` `@` で始まるとExcel等が数式として実行しうる | 静的確認(`=HYPERLINK(...)` がそのまま出力される) | 該当セルの先頭に `'` を付ける |
| S6 | スタンドアロン版プロファイリング画面の `target` / `run_id` を `..` で辿り、トレース用ディレクトリの外の `.json` を読めた(低) | `target=".."` で `traces/../secret.json` | 解決したパスがトレース用ディレクトリの内側でなければ空を返す |

## 要確認(直していない。判断が要る)

| ID | 内容 | 現状の判断 |
|---|---|---|
| Q1 | heartbeat / ci-success / アラート受信に認証が無い。同じPCの任意のプロセスが偽の信号を送れる | ローカル専用が前提の設計。同じユーザーのプロセスは、もともとHubの状態ファイルも触れる。LAN公開や外部ミラー(C7)を始めるときに、トークン認証を足すか判断する |
| Q2 | `--host 0.0.0.0` 等で起動すると、そのネットワークの誰でも起動・同期・アラート操作ができる | 起動時に警告を出す。特定のIPで起動した場合は、そのIPを自動で許可リストへ足す。ワイルドカードは足さないので、実際に開くホスト名を `HUB_ALLOWED_HOSTS` に指定する |
| Q3 | 受信するアラートの**件数**に上限が無い(署名を変え続けると増え続ける。未解消のものはpruneされない) | ローカルでは低リスク。公開するなら件数の上限またはレート制限を入れる |
| Q4 | Originの検査はスキームを見ない。TLSを終端するリバースプロキシの後ろでは、Hostが一致していれば通る | プロキシが Host を書き換える場合は `HUB_ALLOWED_HOSTS` で合わせる |

## 却下(問題にならないと判断した。根拠つき)

| ID | 疑い | 根拠 |
|---|---|---|
| R1 | Webhook経由のSSRF | 宛先URLは環境変数のみで、リクエストからは指定できない |
| R2 | `repos.yaml` の `command` / `branch` 経由のコマンド・オプション注入 | 実行するのは `repos.yaml` の固定値のみで、HTTPリクエストから文字列を受け取らない。`repos.yaml` を書き換えられる攻撃者は、すでにローカルでコードを置ける |
| R3 | アラート本文経由のXSS | Jinjaの自動エスケープ。JSは、サーバーが描いたHTML断片を差し替えるだけで、外部の値を直接 `innerHTML` に入れていない(`tests/test_security.py` で `<script>` / `onerror` を含む本文が文字として出ることを確認) |
| R4 | SQLインジェクション | SQLiteへの書き込みは全てプレースホルダ。文字列連結のSQLは無い |

## 使い方の変更(破壊的になりうる点)

- Hostの許可リストを入れたため、**`127.0.0.1` / `localhost` / `::1` 以外のホスト名・IPでHubを開いている場合は、環境変数
  `HUB_ALLOWED_HOSTS`(カンマ区切り)にそのホスト名を足す**必要がある(足さないと 403。メッセージに直し方を出す)。
  既定の使い方(`uv run hub` → `http://127.0.0.1:8790`)は変わらない。
- 別のツールからHubへ送る側(ProfilingToolのSink等)は、ブラウザではなくOriginを付けないので影響しない。
